## Current behaviour

`pairSeparateInterest` selects candidate interest transactions by `userId`,
`accountId IN (source accounts of these payments)`, `categoryId = the loan's
interestCategoryId` and a date window. Nothing ties a row to the loan being
analysed. Two loans paid from the same chequing account that share one interest
category therefore each collect **both** loans' interest: `100` for loan A and
`200` for loan B near the same date are summed to `300` when detecting either,
and both inferred rates are wrong.

The existing comment claims the `sourceIds` restriction stops bleed-through
("so a shared interest category on another loan cannot bleed in"). It only stops
bleed from a *different* source account; the shared-account case is exactly what
it misses. Confirmed present at `main` `4e48a767`.

## Proposed behaviour

Option A -- **refuse when ambiguous** (recommended). Before accumulating, detect
that another loan/mortgage account of this user shares both the source account
and the interest category. If so, leave `interestAmount` as `null` for the
affected periods, so detection reports "not enough payments with interest
details" rather than a wrong rate.

Option B -- **attribute by payment linkage**. Use `linkedTransactionId` (or the
principal transfer's target account) to associate each interest expense with a
specific loan's payment, and count only rows that resolve to this loan.
Correct when the ledger carries the linkage, but a separately booked interest
expense is by definition *not* a split leg of the transfer, so for many ledgers
there is no linkage to follow and this silently degenerates into Option A
anyway.

Option C -- **split proportionally** across the loans sharing the category.
Rejected as inventing data.

## Alternatives considered

Requiring users to give each loan its own interest category, and surfacing that
as a validation error on the account form. This is a product/UX change rather
than a detection fix, and it would break existing accounts that share one
category, so it is not proposed -- but if you prefer it, that changes the answer
here to "no code change in the detector".

## Recommendation

Option A, with Option B layered only where linkage genuinely exists. Under
`CLAUDE.md`'s missing-data rule a figure that cannot be attributed is *unknown*,
not a sum; reporting `300` as one loan's interest is the failure mode the rule
exists to prevent. Refusing is visible to the user and recoverable; a wrong rate
is neither.

## Risks

- Option A **removes** rate detection for users who today get a (wrong) answer
  on loans sharing a source account and category. That is a visible loss of
  function, even though what is lost is incorrect.
- Detecting the ambiguity needs an extra query over the user's loan accounts on
  a path that currently issues one query; cost is small but non-zero.
- Option B risks the opposite error: partial linkage would attribute some rows
  and silently drop others, producing an understated interest figure, which is
  worse than refusing.
- No stored data or migration is affected.
