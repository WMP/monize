## Current behaviour

When a loan rate changes, LoanRateChangesService.buildScheduledUpdate recomputes the linked scheduled payment and its update() path DELETES and RECREATES every split. To avoid losing recurring overpayments, it re-recognizes extra-principal transfer legs via isExtraPrincipalSplit, which matches on (a) account.overpaymentCategoryId === split.categoryId, (b) a configured account.overpaymentMemo substring, or (c) the literal English substring 'extra' in the memo. The category-based path (a) can never survive the rebuild: a transfer split carrying a category_id is rejected by the DTO's documented mutual-exclusivity, by both createSplits persistence layers (which null it), and by the database CHECK constraint chk_scheduled_split_kind_exclusive (transfer ⟹ category_id IS NULL). The memo paths (b),(c) do round-trip because memo is preserved. Net effect: an overpayment recognized only by its configured category, or one whose memo is localized/user-defined and not configured as overpaymentMemo, is silently dropped on the next rate update or deletion, reducing future principal payments.

## Proposed behaviour

Recognize and preserve extra-principal splits by a stable, round-trip-safe mechanism so that updating or deleting a rate row never removes a valid recurring overpayment, regardless of memo language or wording.

## Alternatives

A) Add a structural marker to scheduled_transaction_splits (e.g. an is_extra_principal boolean, or a dedicated split subtype) via a new migration + schema.sql + entity + DTO + frontend types + support-backup rules; recognize/preserve by that flag. Robust and locale-proof, but requires off-limits schema/migration changes AND a decision on how the flag is set when a user creates an overpayment split. B) Relax the mutual-exclusivity invariant so a transfer split may also carry a category_id: change the CHECK constraint, the DTO validators/docs, both createSplits paths, and audit the posting path, frontend display, and backup classification. Makes overpaymentCategoryId recognition work but is a broad, app-wide data-model semantics change. C) Accept memo-based recognition only: drop/redefine overpaymentCategoryId as a recognition mechanism and document that overpayments must be labelled via a configured overpaymentMemo. Smallest surface, no schema change, but keeps a heuristic the finding criticizes and leaves unconfigured/localized memos unaddressed. D) Infer structurally by shape: treat every transfer-to-loan leg beyond the single recomputed regular-principal leg as extra. No schema change and label-agnostic, but relies on reliably identifying the regular-principal leg after a delete-and-recreate (ordering/amount are not stable anchors), risking mis-allocation of principal in a money calculation.

## Recommendation

Option A (a structural marker column). It is the only choice that is locale-proof, survives the delete-and-recreate rebuild by a stable identifier, and keeps the existing transfer/category mutual-exclusivity invariant intact (which the posting path, frontend, and DB constraint all depend on). It must be paired with a decision on how the marker is set at split-creation time (UI + DTO). If a schema change is not acceptable now, Option C is the safe interim: it changes no data-model semantics and documents the known limitation, but does not fully close the finding.

## Risks

This is a personal-finance money path: a wrong choice silently reduces principal payments (Option D's mis-allocation risk) or, if the transfer+category combination is forced through as the two prior attempts did, causes production INSERTs to fail the CHECK constraint. Option B widens what a transfer split can mean everywhere in the app and risks regressions in posting, reporting, and de-identified backups. Any schema option (A/B) touches database/migrations/** and schema.sql, which are gated.
