## Alternatives

**Attempt 1** (`8f0a0a4ee`) was rejected:

The confirmation calls `applyScheduledPayment(account.id)` without the hash returned by creation. The API consequently posts an empty body, and the backend only compares hashes when `expectedPreviewHash` is defined. For example, after a user previews a payment at 4.9%, another tab can change the current timeline to 5.5%; confirming the original dialog then recomputes and applies the 5.5% split without rejecting the stale preview.

**Attempt 2** (`777aefbb8`) was rejected:

hashScheduledPaymentPreview hashes only the scheduled transaction ID and aggregate proposed amounts. buildScheduledUpdate also applies each extra-principal split's individual amount, category, tags, and memo. For example, if the preview was generated with two extra splits of $40 and $60, another tab can change them to $50 and $50. The aggregate extraPrincipal and every hashed field remain unchanged, so confirmation accepts the stale hash and writes the newer $50/$50 split instead of the $40/$60 state underlying the preview.

**Attempt 3** (`e75bdc6da`) was rejected:

Freshness checking remains conditional on `expectedPreviewHash !== undefined`, while the request DTO also marks the hash optional. A legacy frontend or REST client can preview a payment at 4.9%, another tab can change the timeline to 5.5%, and then confirm using an empty body. The service skips the comparison and applies the newly computed 5.5% payload. The added test explicitly preserves this bypass as “backward-compatible.”
