## Current behaviour

persistSegments (rate-change-inference.service.ts:642) saves inferred LoanRateChange rows with only effectiveDate, annualRate, newPaymentAmount, and source. No record is kept of the account configuration (interestBookingMode, interestCategoryId, paymentFrequency, isCanadianMortgage, isVariableRate) or transaction revision used. If any of those inputs change after detection runs, stale inferred rows remain active and drive schedules and reports using results from an incompatible input revision.

## Proposed behaviour

Store a configuration fingerprint alongside each inferred row, and exclude or delete rows whose fingerprint mismatches the current configuration whenever detection is re-run or when relevant account fields are updated. Per docs/financial-calculation-contract.md section 5: 'When any declared input changes, the old result must be versioned, recomputed, or excluded. Never silently reused.'

## Alternatives

A) Full fingerprint column on loan_rate_changes (new VARCHAR/hash column, migration, schema.sql change) — most faithful to the contract, but requires a schema migration. B) Transactional delete of inferred rows inside accounts.service.ts whenever interestBookingMode, interestCategoryId, or paymentFrequency change — no schema change, but silent loss of the inferred timeline with no UI indication and does not address transaction-data staleness. C) No change — treat re-running detection as a manual user action; document as a known limitation.

## Recommendation

Approach A (fingerprint column) is the correct long-term fix per the financial contract. Approach B is lower-risk for a near-term patch if the schema change cannot be scheduled immediately, but still changes visible behaviour. Either way, decide: (1) which account fields belong in the fingerprint, (2) whether a fingerprint mismatch triggers silent exclusion or a visible staleness marker, and (3) whether transaction-data changes (adds, edits, voids) need to be captured in the fingerprint.

## Risks

Approach B deletes previously inferred rows without recomputing them, which may leave a loan account with no inferred history until the user manually re-runs detection — confusing if the deletion is silent. Approach A adds a new NOT NULL column, so the migration must backfill existing rows with a sentinel fingerprint that will be treated as stale on first re-run.
