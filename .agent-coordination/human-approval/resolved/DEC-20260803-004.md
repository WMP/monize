## Current behaviour

`pairSeparateInterest` sums `Math.abs(Number(tx.amount))` over every non-void,
non-transfer transaction in the loan's interest category near a payment date.
`Math.abs` erases the sign, so a **refund increases interest**: a `-200` charge
and a `+50` refund in the same period are reported as `250` of interest, not
`150` or `200`. The inflated figure then drives the inferred annual rate shown
to the user and offered as the loan's detected rate.

Confirmed present at `main` `4e48a767` (line moved from `:462` to `:477` after
the REV-20260803-008 fix landed on the fix branch).

## Proposed behaviour

Option A -- **net the period** (recommended). Sum signed amounts and negate:
`interest = -(sum of signed amounts)`, clamped out if the result is `<= 0`.
The example yields `150`.

Option B -- **exclude inflows**. Skip any transaction whose signed amount is not
an expense; the example yields `200`.

## Alternatives considered

Option C -- treat a period containing a refund as **unknown** (`interestAmount`
stays `null`, no rate observation from that period). Consistent with the
missing-data rule in `CLAUDE.md`, but it discards a period the user can read
correctly off their own ledger, and refunds are common enough (fee reversals,
corrections) that this could silence rate detection on an otherwise healthy
loan.

## Recommendation

Option A. Interest actually borne in the period is the charge net of its
reversal, which is what a rate should be inferred from, and it is the only
option that cannot be gamed by splitting one charge into a charge plus a
correction. Option B is defensible only if refunds are assumed to relate to
earlier periods -- which the code cannot know, since it pairs purely by date
proximity.

## Risks

- Any option changes a **money figure and the inferred rate** already shown to
  users, so previously detected rates may shift on loans whose ledger contains
  refunds in the interest category.
- Option A can produce a small or near-zero net for a period that is mostly
  reversal, which the `summed <= 0` guard drops -- that period then yields no
  rate observation. This is correct but reduces the number of observations.
- No migration or stored data is affected; detection is computed on read.
