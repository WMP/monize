## Why this is a decision and not a fix

`REV-20260803-017` names two defects. The first -- a row whose date already
carries a saved rate change opened the Add flow and failed on the duplicate-date
conflict -- is unambiguous and is **fixed** on the fix branch. The second is not:
the finding asks to "omit `onEdit` for historical rows", and the repository
contradicts itself about whether that affordance is wanted.

## Current behaviour

`ScheduleTableRow` offers the rate-edit button whenever `editing` is supplied and
the row has a rate, projected or historical. Clicking a **historical** row opens
the Add form seeded with that row's date and rate.

Two artifacts disagree about whether that is correct:

- The component's own doc comment: "Historical and aggregate rows show their rate
  read-only (it is observed from the interest charged); only projected rows
  expose the inline rate editor."
- A passing test, `AmortizationScheduleTable.test.tsx:359`, "opens the
  rate-change form pre-filled when a historical rate is clicked", whose comment
  reads "The rate value is a button that opens the add form seeded with the
  row's date and rate -- no inline editing."

The test is specific enough that someone built this on purpose. The doc comment
is equally specific that they should not have. Confirmed both present at `main`
`4e48a767`.

Note that a historical row *can* legitimately be a change point: `rateChanges`
are matched by date against history rows too, so the fixed half already routes
those to Edit. This decision is only about a historical row with **no** saved
change on its date.

## Proposed behaviour

Option A -- **keep it** (recommended). A historical row is a plausible place to
say "the rate changed here and I never recorded it", which is exactly the
back-fill case a personal-finance app should make easy: the user is reading their
own past payments and noticing the rate moved. Nothing is written until they save
the form, so the affordance cannot corrupt anything. Fix the doc comment instead,
which is the artifact with no test behind it.

Option B -- **remove it**, as the finding asks. Historical rates are observed
from interest actually charged, so inviting an edit there implies the past can be
rewritten. Requires deleting the test at `:359` and its intent.

## Alternatives considered

Option C -- keep the affordance but relabel it for historical rows ("Record a
rate change from this date") so it reads as back-filling rather than editing
history. Costs a new catalog string in every locale, and the current label
`editRateLabel` is already date-qualified.

Option D -- allow it only for a historical row inside the current rate period
(where a back-fill is most likely meaningful). More rules for little gain, and
the boundary is itself a judgement call.

## Recommendation

Option A, and correct the doc comment in the same change. I am not implementing
it: the finding explicitly asks for the opposite, so the reviewer and the
maintainer should settle which artifact is authoritative rather than have me pick
the one I find more persuasive.

## Risks

- Option A leaves `REV-20260803-017` partly unimplemented, so a future audit may
  re-raise it. The doc-comment correction is what stops that.
- Option B removes a discoverable path to back-filling rate history. The Rate
  History sidebar's Add button remains, so the capability is not lost, only the
  shortcut from the row the user is already looking at.
- Either way this is presentation only -- no stored data, no calculation, and no
  API behaviour changes.

## Exact decision needed

Should a historical schedule row with no saved rate change on its date keep its
rate-edit button (Option A, plus a doc-comment fix), or lose it (Option B, plus
deleting the test at `AmortizationScheduleTable.test.tsx:359`)?


## Withdrawn

No decision is needed: `REV-20260803-006` was closed without a code change, so there is nothing to approve.
