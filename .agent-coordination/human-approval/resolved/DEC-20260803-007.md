## Current behaviour

`recalculatePaymentForRate` (`backend/src/loan-rate-changes/loan-rate-changes.service.ts`,
lines 602-624) always uses `Math.abs(Number(account.currentBalance))` -- **today's**
live balance -- as the starting balance, while correctly deriving the
remaining-amortization term from `effectiveDate` via `monthsBetweenYmd`. The two
inputs to the payment formula are therefore date-consistent for the term but not
for the balance, whenever `effectiveDate` is not today:

- A change effective two years in the future combines today's (higher) balance
  with the shorter remaining term that will exist in two years, overstating the
  new payment.
- A past-dated change combines today's (lower) balance with the longer
  remaining term that existed back then, producing a different (generally
  understated relative to what should have applied) payment than the correct
  historical one.

Only reachable for `AccountType.MORTGAGE`, only when the caller passes
`recalculatePayment: true` (as opposed to supplying `newPaymentAmount`
directly). Called from `create()` (line ~150) and, via its default
`recalculatePayment: newPaymentAmount == null`, from the legacy
`AccountsService`/`loan-mortgage-account.service.ts` `updateMortgageRate` path.

Confirmed present at fix-branch HEAD (`5e4464b9`); re-verified against the
current code, not merely the original source_sha.

There is no existing "balance at an arbitrary date" utility anywhere in the
codebase (confirmed by grep across `backend/src` for
`balanceAsOf|historicalBalance|projectBalance|balanceAtDate|getBalanceAt` --
zero matches; `mortgage-amortization.util.ts`/`loan-amortization.util.ts` only
project forward from a given starting balance/date, they do not reconstruct or
project the actual balance as of an arbitrary date against the account's real
transaction/rate-change history).

## Proposed behaviour

Option A -- **derive the balance at `effectiveDate`**. Reconstruct it from
historical transactions for a past date (ledger replay), or project it via
amortization from today's balance/rate/payment forward to a future date,
folding in every intervening rate-change/payment-timeline row along the way.

Option B -- **restrict automatic recalculation to `effectiveDate === today`**
(recommended). For any other effective date, reject `recalculatePayment: true`
with a validation error and require the caller to supply an explicit
`newPaymentAmount`. Closes the reported overstatement/understatement
immediately with no new financial modeling.

## Alternatives considered

Option C -- keep automatic recalculation available for any date, but only
using a balance snapshot actually recorded on the `LoanRateChange` row at
creation time (a new column), falling back to Option B when none exists. This
still requires a schema/data decision and does not retroactively fix rows
that predate the column, so it only partially closes the gap and adds
migration surface -- out of scope for a routine bug-fix pass regardless of
which option is chosen.

## Recommendation

Option B as an immediate, low-risk fix, with Option A (or C) deferred to a
separately specced financial feature if product wants full past/future
support. Option A is new financial logic, not a bug fix -- it has its own
missing-data questions (incomplete transaction history, an account opened
after the effective date, multiple intervening rate changes) that
`docs/financial-calculation-contract.md` would require a short approved spec
for before implementation, per this repo's convention for financial features
of any substance.

I am not confident Option B is the right product tradeoff without knowing how
often users backdate or forward-date a rate change with automatic
recalculation in practice, or what the current frontend UX offers for
`effectiveDate` when `recalculatePayment` is checked -- that UX was not
inspected as part of this investigation (out of the investigating subagent's
partition and concurrently being edited by another agent this round).

## Risks

- Option B is a behavior change: requests that previously succeeded (with a
  wrong number) for a non-today effective date now fail validation and
  require an explicit payment. This could break an existing legitimate
  workflow (e.g. a user backdating a rate change discovered late, or entering
  a known future renewal rate) that currently "works" with an incorrect
  number.
- Option A is a nontrivial new financial calculation with its own correctness
  surface (see above) and would need its own spec, truth table and test
  matrix before implementation, per `docs/financial-calculation-contract.md`.
- No migration or stored data is affected by either A or B; the payment is
  computed on write, not stored historically per rate change.
