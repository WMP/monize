## Current behaviour

This is not an ordinary product-tradeoff decision. It is a factual dispute
between the two automated agents about what the current source code says,
and it has not resolved after three rounds of dispute-and-rejection.

REV-20260803-032 claims: "The fallback lower bound is the first loan-account
transaction... interest expenses are filtered out." The review agent has
rejected the fix agent's dispute of this finding three times (at
`2026-08-03T22:35:06Z`, `23:22:45Z`, and `2026-08-04T05:07:28Z`), each time
repeating substantially the same claim: that a variable named `originationDate`
is derived from `paymentStartDate ?? sortedTransactions[0].transactionDate`
and used as a **lower bound** filter on `scopedInterestTransactions`.

The fix agent has, across three independent investigations (two by separate
subagents, one by the orchestrating agent reading the file directly), found:

- No identifier `originationDate` exists anywhere in this repository (`grep -rn
  originationDate frontend/ backend/` returns zero matches in source; the only
  hit is a comment in `loan-history.test.ts` explaining its absence).
- `paymentStartDate` is never referenced in `loan-history.ts`.
- The actual code (quoted verbatim, current fix-branch HEAD `e761d855`, lines
  100-142):

  ```ts
  const currentBalance = debtMagnitude(Number(account.currentBalance) || 0);
  ...
  const lastTransactionDate =
    sortedTransactions.length > 0
      ? sortedTransactions[sortedTransactions.length - 1].transactionDate.split('T')[0]
      : null;
  const loanPaidOff = currentBalance <= 0.01;
  const scopedInterestTransactions = interestTransactions.filter((tx) => {
    if (!loanPaidOff || !lastTransactionDate) return true;
    return tx.transactionDate.split('T')[0] <= lastTransactionDate;
  });
  ```

  This applies exactly one filter, and it is an **upper** bound
  (`lastTransactionDate`, the *last* transaction, not the first), gated on the
  loan being **already paid off** (`loanPaidOff`). It never filters by a lower
  bound of any kind, and the surrounding comment (lines 124-133) explicitly
  documents the opposite of what the finding/rejections describe: "include all
  of it regardless of date... those payments must still show and count...
  rather than being truncated at a start date... The only bound kept is the
  upper one for a fully paid-off loan."
- One subagent additionally *injected* the exact lower-bound logic the
  rejections describe directly into the file and confirmed it breaks the
  existing test suite (3 tests fail) -- proving the described bug pattern is
  detectable by the current tests, and that current code does not have it.

## Why this needs a human rather than a fourth dispute round

Both agents cannot be reading the same text and disagree this consistently;
either the review agent is evaluating a different revision, a stale cache, or
a description that was never grounded in this file's literal text, or the fix
agent's repeated quoting/injection tests are themselves mistaken in a way
neither side has been able to surface after three rounds. This is a case
where the git repository being the only channel between the two agents has
stopped working -- more rounds of the same dispute are not likely to add new
information.
