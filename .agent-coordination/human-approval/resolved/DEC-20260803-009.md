## Current behaviour

Three prior fix passes on REV-20260803-028 progressively fixed
`loan-rate-changes.service.ts`'s recognition and rebuild of a scheduled
transaction's extra-principal split (memo-substring-only recognition, then
dropped `categoryId`/`tags` on rebuild, then only-first-split-preserved). Each
fix was correct at that file's own boundary, and each was reopened by the
review agent finding the next real bug.

The fourth reopen traced the root cause past that file's boundary, into
`scheduled-transactions.service.ts`'s `createSplits`, which nulls `categoryId`
on any split whose `kind` is inferred as `TRANSFER` (i.e. any split carrying a
`transferAccountId`, which every extra-principal split does). Investigated and
confirmed this is not an oversight to patch: it is enforced at three
independent layers --

- **A live Postgres CHECK constraint** (`schema.sql` lines 490-511,
  `chk_scheduled_split_kind_exclusive`, introduced in migration 063 and never
  loosened since; the identical pattern, `chk_split_kind_exclusive`, exists on
  the ordinary posted `transaction_splits` table too, from migration 062):
  `kind = 'transfer' AND category_id IS NULL AND ...` -- a transfer split
  carrying both a `transferAccountId` and a `categoryId` is a constraint
  violation, not merely an app-level convention.
- **The DTO's own documentation** (`create-scheduled-transaction-split.dto.ts`
  line 37): `transferAccountId` is explicitly documented as "mutually
  exclusive with categoryId / investment".
- **`createSplits` mechanically enforcing it** at persistence time.

So `loan-rate-changes.service.ts`'s `isExtraPrincipalSplit` category-based
recognition branch (`split.categoryId === account.overpaymentCategoryId`) is
not a bug with a code fix -- it is checking a field that the data model
guarantees will always read back `null` for this split shape, on every sync
after the first. It was never going to hold across a second synchronization,
by design of the schema, not by omission in the service.

`tagIds` and `memo` DO survive persistence unconditionally for a TRANSFER
split (no kind-based constraint on either) -- confirmed by reading
`createSplits`'s tag-assignment block (lines 745-750, runs regardless of
`kind`) and the memo column (plain `text`, no constraint).

## Proposed behaviour

**Option A -- recognize by a dedicated marker tag (recommended).** Every
extra-principal split `loan-rate-changes.service.ts` creates or rebuilds gets
a consistent, internally-managed tag attached (e.g. a reserved tag id/name the
service owns), and recognition reads that tag's presence instead of
`categoryId`. This is the one channel that (a) survives persistence
unconditionally for a transfer split, and (b) doesn't depend on the user's own
memo wording matching anything -- closing the finding's original complaint
("Additional principal", a localized memo, or any user-chosen label) without
relying on memo matching at all.

**Option B -- memo-only recognition**, dropping the dead `categoryId` branch
and relying on (in order) the account's configured `overpaymentMemo`
substring, then the literal `"extra"` fallback. Simpler, no new tag-management
code, but does not close the finding's core complaint: a user-authored memo
that matches neither the account's configured substring nor the literal
`"extra"` (the finding's own example) is still unrecoverable on the next sync.
This only narrows the bug, it does not fix it.

**Option C -- store a stable, structural association elsewhere** (e.g. a
column on `LoanRateChange` or a dedicated table linking a rate row to "its"
extra-principal split by id, rather than re-deriving recognition from split
content every sync). Most robust against future memo/category edits by the
user, but is a real schema/data-model change (new column or table), a bigger
change than this finding's severity plausibly justifies on its own, and would
need its own migration and test-matrix per `docs/financial-calculation-contract.md`.

## Alternatives considered

Keeping `categoryId`-based recognition and instead trying to make
`createSplits` stop nulling it for this one caller was investigated and
rejected outright -- it is not a "smallest correct fix," it is a live
constraint violation (a 500 error on every affected INSERT), strictly worse
than the current silent-drop bug.

## Recommendation

Option A. It's the smallest change that actually survives round-trips and
removes the dependency on user-authored memo text entirely, without a schema
change. Category-based recognition should be removed from
`isExtraPrincipalSplit` (it is dead code for this data shape, not a
degraded-but-working fallback) rather than left in confusingly.

## Risks

- Whichever option is chosen, this is a change to how an existing recognition
  mechanism works, on a path that deletes/replaces a scheduled transaction's
  splits -- getting it wrong risks silently dropping a real overpayment again,
  which is exactly this finding's failure mode. Needs the same fail-then-pass
  discipline the prior four passes used, but this time with a regression test
  that actually exercises persistence (the fourth reopen also caught that the
  third pass's own regression test faked a "second sync" by feeding back its
  own mocked input rather than anything that went through real persistence --
  a correct test must simulate `createSplits`'s actual categoryId-nulling, or
  better, exercise it directly).
- The same investigation flagged (not confirmed, not yet acted on) that
  `backend/src/transactions/transaction-split.service.ts`'s real (posted, not
  scheduled) transfer-split path also unconditionally nulls `categoryId` --
  meaning `frontend/src/lib/loan-history.ts`'s `isOverpayment`/
  `matchesOverpaymentCategory`, which recognizes a *posted* overpayment
  transaction the same way, may have the identical structural problem for
  real transaction history, not just scheduled templates. This needs its own
  investigation and is out of scope for this decision, but is a live risk to
  the correctness of overpayment detection across the app if confirmed --
  flagging prominently since it wasn't part of the original finding at all.

### Round 16 follow-up: investigated, not a live bug

Confirmed the structural half of the concern above: `transaction-split.service.ts`'s
`createSplitsInternal` nulls `categoryId` on a posted transfer-kind split for
the identical reason as the scheduled path -- the real `chk_split_kind_exclusive`
constraint (migration 062, the posted-table sibling of
`chk_scheduled_split_kind_exclusive` cited above) forbids a transfer split
from carrying a `categoryId`.

This is **not currently a live user-facing bug**, though. `isOverpayment`/
`matchesOverpaymentCategory`'s dominant, UI-reachable recognition path reads
`Transaction.categoryId` -- the parent transaction's own category, set via
the plain-transfer path (`TransactionTransferService.createTransfer`), which
carries no such constraint -- not `TransactionSplit.categoryId`. The
constrained field is only read when a user categorizes the *transfer leg of a
split transaction* specifically, a combination `SplitEditor.tsx`'s own UI
does not offer (a split's transfer leg is not exposed with a category
picker). So the dead-on-persistence field is also dead on the read side
today; there is no live path that writes a category to it, reads it back,
and gets surprised by `null`.

Recommendation: no new finding is warranted. At most, worth a minor
consistency/hardening note (e.g. a comment at `TransactionSplit.categoryId`'s
declaration, or in `isOverpayment`, pointing at the constraint) so a future
change to `SplitEditor.tsx` that *did* expose a transfer-leg category picker
would be flagged as reintroducing exactly this dead-write shape -- but that
is cleanup, not a correctness fix, and is not being done as part of this
decision.
