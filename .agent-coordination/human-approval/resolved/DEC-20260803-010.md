## Current behaviour

`ScheduledPaymentPreview` (`loan-rate-changes.service.ts` lines 36-51) is pure
display data -- no id, version, or hash binding it to anything:

```typescript
export interface ScheduledPaymentPreview {
  scheduledTransactionId: string;
  scheduledTransactionName: string | null;
  currencyCode: string;
  currentPaymentAmount: number | null;
  proposedPaymentAmount: number;
  currentPrincipal: number | null;
  proposedPrincipal: number;
  currentInterest: number | null;
  proposedInterest: number;
  extraPrincipal: number;
}
```

`create()` (with `deferScheduledSync: true`, which the controller always
passes) computes this preview once and hands it back; nothing about it is
persisted. `applyScheduledPaymentSync()` (lines 417-437), the confirm step,
takes only `accountId` -- no rate-change id, no version, no hash -- and
re-resolves everything live: the current rate-change timeline
(`resolveCurrentTimeline`, re-reads every `LoanRateChange` row), the account's
own scalar fields, and the linked scheduled transaction's current splits
(`buildScheduledUpdate`, which re-fetches via
`scheduledTransactionsService.findOne`). Confirmed by reading the controller
(`POST .../apply-scheduled-payment` takes no request body at all) and the one
frontend caller (`loanRateChangesApi.applyScheduledPayment(accountId)`,
`useLoanRateEditing.ts`) -- the client-held preview is display-only and never
sent back.

So: if another tab (or the same session) edits a `LoanRateChange` row, the
account's rate/payment, or the linked scheduled transaction's splits between
the preview being shown and confirm being clicked, confirming applies
whatever is current, silently, not what the user approved.

## Proposed behaviour

**Option A -- monotonic version counter on `LoanRateChange`.** Cheap, no new
crypto, but only covers drift in the rate-change row itself -- misses
concurrent edits to the account's own scalar fields or the scheduled
transaction's splits, which the finding explicitly names as in scope.

**Option B -- signed hash of the resolved inputs (recommended).** Compute an
HMAC over a canonicalized serialization of everything `buildScheduledUpdate`
actually reads (the resolved rate/payment, account balance/frequency, the
scheduled transaction's current splits), return it alongside the preview,
require it back on confirm, recompute and reject with a fresh preview on
mismatch. Covers every drift source the finding names; no schema change
(stateless, computed both times); must be HMAC-signed, not a bare hash, or a
malicious client could forge a hash matching current state to always
"confirm clean."

**Option C -- client echoes back a signed descriptor carrying the exact
resolved values (reusing `backend/src/ai/actions/ai-action-signing.service.ts`'s
pattern: `canonicalize()` + HMAC, `actionId` + `expiresAt` + single-use
consumption via an in-memory map).** This codebase already has exactly this
mechanism for AI-proposed writes. It solves tamper/replay/expiry but, as
implemented there, does NOT reject on live-state drift -- it applies the
signed values unconditionally. Reusing it verbatim would need an added
freshness check on top (making it effectively B+C) if "reject and return a
fresh preview" (the finding's literal wording) is the desired behaviour
rather than "apply exactly what was approved regardless of what changed
since."

## Alternatives considered

Combining B and C (sign the resolved values AND reject if live state has
since diverged) was considered and is arguably the most complete answer, but
is also the largest change -- new request/response shapes on both ends, a new
signed-descriptor concept for this module. Investigated whether the AI-actions
signing service could simply be reused directly (same secret, same helper);
recommend against sharing it as-is (unrelated feature coupling to a
security-sensitive AI-write-confirmation mechanism) -- a sibling instance with
its own key/label would be cleaner if C's approach is chosen.

## Recommendation

Option B. It covers every drift source named in the finding without a schema
change, and it matches the finding's literal recommended behaviour (reject
stale, return fresh) rather than C's "apply what was signed regardless"
semantics, which is a bigger, more debatable behavior change deserving its
own separate product decision if ever wanted.

## Risks

- **Every option changes the `apply-scheduled-payment` endpoint's request
  contract**, which today accepts no body at all. This is a breaking change
  to a shipped endpoint with exactly one caller
  (`useLoanRateEditing.ts`/`loanRateChangesApi.applyScheduledPayment`) --
  contained blast radius, but must ship atomically with that frontend update,
  not staged.
- **Option A** alone would pass tests while leaving the account-scalar and
  scheduled-transaction-split race open -- a false sense of the finding being
  closed.
- **Option B** needs the hash's field set to exactly match what
  `buildScheduledUpdate` reads -- too few fields reopens the gap, too many
  (e.g. an unrelated `updatedAt` tick) causes false-positive rejections on
  every confirm. Needs its own adversarial test matrix per
  `docs/financial-calculation-contract.md` before being considered closed.
- **Option C** raises a signing-key-ownership question (new key vs. reusing
  the AI-actions one) and, unmodified, does not actually reject on drift --
  it would need the same field-coverage care as B if a freshness check is
  layered on top.

## Affected files

Backend: `loan-rate-changes.service.ts` (`ScheduledPaymentPreview`,
`buildScheduledUpdate`, `applyScheduledPaymentSync`, `create`),
`loan-rate-changes.controller.ts` (needs a request DTO where today there is
none), a new confirm-request DTO, and (Option B) a small canonicalize/HMAC
helper modeled on `ai-action-signing.service.ts`. `loan-rate-changes.service.spec.ts`
needs new adversarial tests for the stale-confirm-is-rejected case.

Frontend: `frontend/src/types/loan-rate-change.ts`, `frontend/src/lib/loan-rate-changes.ts`,
`frontend/src/components/accounts/loan-detail/useLoanRateEditing.ts` (needs to
carry the new token through and handle a "stale, here is a fresh preview"
response rather than just toasting an error), plus their tests
(`LoanRateControls.test.tsx`, `RateHistorySidebar.test.tsx`,
`frontend/src/app/accounts/[id]/page.test.tsx`, `loan-rate-changes.test.ts`).

## Decision needed

Pick A, B or C (or B+C) for the staleness-detection mechanism; confirm the
exact field set the freshness check must cover (must include at minimum: the
resolved rate-change timeline, the account's rate/payment/balance/splits, and
the linked scheduled transaction's current splits); pick the HTTP status and
response shape for a rejected-as-stale confirmation (409 with the fresh
preview inline, recommended, vs. a bare 409 forcing a separate re-call); and
sign off that this ships as a breaking change to
`POST /accounts/:accountId/rate-changes/apply-scheduled-payment`'s request
body, coordinated with the one frontend caller in the same change.
