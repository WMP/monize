## Current behaviour

`pairSeparateInterestByDate` in `frontend/src/lib/loan-history.ts` (lines
824-848) accumulates `Math.abs(Number(tx.amount))` over every non-transfer
transaction in a loan's interest category on its source account, paired to
the nearest payment date within a tolerance window. A `-100` interest charge
and a `+20` refund/credit in the same category and pairing window both
contribute their absolute value, reporting `120` of interest for that period
instead of the net `80`. The single-orphan path (line ~290) has the identical
defect for an unpaired refund.

This figure feeds `LoanPaymentEvent.interest`, `LoanHistoryResult.cumulativeInterest`
(shown throughout the loan detail page, `DebtPayoffTimelineReport`,
`LoanOverpaymentSimulatorReport`, and PDF/CSV export), and
`assignObservedRates`'s `periodicRate = event.interest / balanceBefore` rate
reconstruction when no rate-change timeline exists.

**This is structurally the same question as DEC-20260803-004**
(`backend/src/accounts/loan-payment-detector.service.ts`'s `pairSeparateInterest`,
related to REV-20260803-023) -- same `Math.abs`-erases-sign pattern, same
date-proximity pairing that cannot know whether a refund belongs to the
charge it's paired with or an earlier period. Investigated whether this
file's specific arithmetic removes that ambiguity and found nothing that
does; the pairing mechanism is identical, just feeding a displayed historical
figure instead of a one-time rate-detection estimate.

## Proposed behaviour

Mirrored from DEC-004 for consistency:

- **Option A -- net the period.** `interest = -(sum of signed amounts)`,
  discarded (treated as 0) if `<= 0`. Example yields `80`.
- **Option B -- exclude inflows.** Sum only the expense (negative) legs,
  ignore refunds. Example yields `100`.
- **Option C -- treat the period as unknown.** A mixed-sign pairing window
  reports no numeric interest for that date. More invasive here than in the
  backend case: `LoanPaymentEvent.interest`/`cumulativeInterest` are currently
  non-nullable numbers consumed unconditionally by every downstream reader
  (rate reconstruction, projections, reports) -- Option C would require
  threading a nullable/"unknown" state through all of them and rendering it
  distinctly per root CLAUDE.md's "an unknown value must not render as a
  measured zero" rule, a materially larger change than A or B.

## Alternatives considered

Resolving this DEC independently of DEC-004, with a different option, was
considered and rejected: the same category of transaction (a refund against a
booked loan-interest expense) would then be netted one way for rate
*detection* (DEC-004's file) and a different way for rate *reporting/history*
(this file) on the same loan -- a user-noticeable inconsistency (two different
"current rate" figures derived from the same ledger, depending only on which
code path computed them).

## Recommendation

Same reasoning as DEC-004 favors Option A -- but the concrete recommendation
is to resolve **both DECs together with the same chosen option**, precisely
to avoid the inconsistency above.

## Risks

- Changes a money figure already on screen (`cumulativeInterest`, per-installment
  interest) for any loan with a refund/credit in its interest category, and
  changes observed-rate reconstruction for loans without a rate-change
  timeline.
- Downstream consumers: `LoanOverpaymentSimulatorReport`, `DebtPayoffTimelineReport`,
  PDF/CSV export.
- Option C is additionally a type-level change rippling through every
  `LoanPaymentEvent.interest` consumer.
