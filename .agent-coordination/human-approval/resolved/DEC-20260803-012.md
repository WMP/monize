## Current behaviour

`frontend/src/lib/loan-history.ts:849`'s standalone-interest fetch (feeding
the same separately-booked-interest aggregation discussed in DEC-004/DEC-011)
scopes candidate transactions by source account and interest category only,
then splits them across loans purely by date-range non-overlap. Two loans
that are both active concurrently, both paid from the same chequing account,
and both tagged with the same general "Loan Interest" category have no
discriminator between them for that overlapping window: each loan's fetch
returns both loans' standalone interest expenses, and both attribute the full
combined amount to themselves.

Confirmed by reading the call site: there is no loan id, no account-linking
field, and no per-transaction marker on the standalone interest transactions
themselves that a query could filter on. The account/category/date-range
scoping is genuinely all the information available today.

## Proposed behaviour

**Option A -- add a nullable loan-linking column** (e.g. on the transaction
or a join table) that, when set, pins a standalone interest transaction to
one specific loan account; unlinked transactions keep today's
account+category+date-range behaviour. Backward-compatible, opt-in, but
leaves the ambiguity unresolved for any user who does not go set the link --
which is every existing transaction and every user who does not know the
feature exists.

**Option B -- enforce one interest category per loan account.** Reframe this
as a data-entry constraint rather than a query problem: if two concurrently
active loans are not permitted to share an interest category (validated at
the account-settings or category-assignment layer), the existing
account+category+date-range scoping becomes unambiguous by construction. No
schema change, but is a behaviour change for any existing user who has
already set up two concurrent loans sharing a category -- their existing data
would need a migration/backfill story or a one-time reconciliation prompt.

**Option C -- persisted association table** linking standalone interest
transactions to a specific loan explicitly (many-to-one, transaction to
loan), populated at transaction creation/categorization time (UI would need a
loan picker whenever a transaction is tagged with an interest category shared
by more than one active loan) and backfilled retroactively is not generally
possible without user input for pre-existing ambiguous transactions. Most
structurally correct, but the largest change: new table, new UI surface, and
an unresolvable backfill gap for historical data.

## Alternatives considered

Attempting to disambiguate algorithmically from existing data alone (e.g.
proportional allocation by loan balance, or "most recent loan wins") was
considered and rejected: any such heuristic invents a specific-dollar
attribution the ledger does not actually support, which is exactly the kind
of fabricated total the root `CLAUDE.md` missing-data doctrine forbids ("a
subtotal is not a total," extended here to "an unverifiable split is not a
verified one"). The honest fallback for an ambiguous window, if no discriminator
is added, is to report the aggregate as unknown/ambiguous for that loan
rather than double-counting it as this loan's own -- but that is itself a
product-visible behaviour change and is listed as part of the decision below,
not assumed.

## Recommendation

No single option is recommended here -- unlike DEC-004/DEC-011, this is not a
sign-netting convention question with a clearly dominant answer; it is a
genuine data-model gap with three structurally different shapes (a nullable
link, a stricter data-entry constraint, or a new association table), each
with different UX and migration implications. This needs product input on
which tradeoff (opt-in linking vs. a new setup constraint vs. new UI surface
for categorization) is acceptable, not a technical judgement call.

## Risks

- Whatever is chosen, existing users with two or more concurrent loans
  already sharing an interest category and source account are currently
  silently double-counting each other's interest today; fixing the query
  without addressing their existing data leaves the historical figures wrong
  even after the fix ships for new data.
- Option B is a behaviour change that could reject or force reclassification
  of an existing valid setup.
- Option C's backfill gap means some historical ambiguity may be permanently
  unresolvable and should surface as "unknown for this period" rather than a
  silently-picked owner, per the missing-data doctrine.

## Affected files

`frontend/src/lib/loan-history.ts` (the standalone-interest fetch at line 849
and its consumers: `LoanPaymentEvent`/`cumulativeInterest` construction,
downstream reports). Option A/C additionally need a backend column/table
(new migration under `database/migrations/`, `database/schema.sql`) and a
frontend UI surface for setting the link. Option B needs validation in the
account/category-assignment path (likely `backend/src/accounts/` and/or
category-assignment DTOs) plus a migration/backfill story for existing
overlapping setups.

## Decision needed

Pick A, B, or C for how a standalone loan-interest transaction should be
disambiguated between two or more concurrently active loans sharing a source
account and interest category; if A or C, decide whether historical
ambiguous transactions render as split-unknown or keep today's (incorrect)
double-attribution until manually resolved.
