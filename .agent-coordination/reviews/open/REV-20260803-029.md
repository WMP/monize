## Location

`backend/src/loan-rate-changes/loan-rate-changes.service.ts:378`

## Failure scenario

The preview is not versioned or passed back on confirmation. applyScheduledPaymentSync re-resolves the current timeline and reloads the schedule. If another tab edits the rate, payment, or extra split after the preview is shown, confirming the old preview applies the newer, potentially different amount and split without the user's authorization.

## Recommended fix

Bind confirmation to a rate-change ID plus an expected timeline/schedule version or payload hash. Reject stale confirmations and return a fresh preview rather than applying changed state.

## Re-review of `8f0a0a4ee2c6`

Not fixed. The confirmation calls `applyScheduledPayment(account.id)` without the hash returned by creation. The API consequently posts an empty body, and the backend only compares hashes when `expectedPreviewHash` is defined. For example, after a user previews a payment at 4.9%, another tab can change the current timeline to 5.5%; confirming the original dialog then recomputes and applies the 5.5% split without rejecting the stale preview.


## Re-review of `777aefbb8f07`

Not fixed. hashScheduledPaymentPreview hashes only the scheduled transaction ID and aggregate proposed amounts. buildScheduledUpdate also applies each extra-principal split's individual amount, category, tags, and memo. For example, if the preview was generated with two extra splits of $40 and $60, another tab can change them to $50 and $50. The aggregate extraPrincipal and every hashed field remain unchanged, so confirmation accepts the stale hash and writes the newer $50/$50 split instead of the $40/$60 state underlying the preview.


## Re-review of `e75bdc6daf9b`

Not fixed. Freshness checking remains conditional on `expectedPreviewHash !== undefined`, while the request DTO also marks the hash optional. A legacy frontend or REST client can preview a payment at 4.9%, another tab can change the timeline to 5.5%, and then confirm using an empty body. The service skips the comparison and applies the newly computed 5.5% payload. The added test explicitly preserves this bypass as “backward-compatible.”
