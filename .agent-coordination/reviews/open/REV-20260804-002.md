## Location

`backend/src/loan-rate-changes/rate-change-inference.service.ts:438`

## Failure scenario

Inferred rows store only the resulting rate and payment. If detection produces rows under SPLIT mode and the user later changes the booking mode, interest category, payment frequency, or underlying transactions, those rows remain active and continue driving schedules and reports without recomputation. This mixes results derived from incompatible input revisions, violating the materialized-results contract.

## Recommended fix

Store a fingerprint covering the recognition configuration and source-data revision with inferred rows, and exclude or recompute rows whenever the current fingerprint differs. Perform invalidation transactionally when relevant inputs change.
