## Location

`backend/src/accounts/accounts.service.ts:743`

## Failure scenario

The update assigns any valid payee UUID directly, and account creation similarly spreads the DTO into the entity. An authenticated user who supplies another user's payee UUID can create a cross-tenant account-to-payee relationship because the foreign key checks only existence. Deleting that other user's payee will then modify the attacker's account through ON DELETE SET NULL.

## Recommended fix

Before create or update, query the payee by both id and userId, using the QueryRunner manager during updates, and reject IDs not owned by the requester.

### fix-agent 2026-08-03 -- fixed in `f70e0314` on `automation/claude-fixes`

**Confirmed still real** at `main` = `4e48a767`. The line number has moved
(`:743` at `source_sha` is now `:737`), so it was re-read rather than patched
blind. Both entry points were unguarded:

- `create` destructures the DTO and spreads `...accountData` into
  `repo.create(...)`, so the payee id lands on the entity untouched.
- `update` had a bare `if (dto.overpaymentPayeeId !== undefined)
  account.overpaymentPayeeId = dto.overpaymentPayeeId;`.

`schema.sql:535-536` confirms the escalation: the FK is `ON DELETE SET NULL`,
so the victim deleting their own payee writes to the attacker's account row.

#### What changed

`assertPayeeOwned(userId, payeeId)` added to `accounts.service.ts`, modelled
directly on the `assertInstitutionOwned` already in that file (same
`findOne({ where: { id, userId }, select: { id: true } })` shape, same
`BadRequestException`). Called from `create` beside the existing institution
check, and from inside `update`'s `if` block.

On the recommendation's "using the QueryRunner manager during updates": there
are no `QueryRunner`s left in `src/` (RLS tasks R1-R7; lint rule L1 bans the
pattern). The equivalent guarantee is met differently and is met -- a nested
`withScopedDb` **joins** the ambient transaction, so the check inside `update`
runs on the same connection, inside the same transaction as the write, and
refuses before it. That satisfies `CLAUDE.md`'s "a rejected command must not
already have written"; the test
`does not store the account when the overpayment payee is rejected` asserts
`manager.save` was never called.

The three create-delegation paths (investment pair, loan, mortgage) are reached
*from* `create` after the assertion, so all of them are covered by the single
call site. `create` and `update` are the only entry points the controller
exposes (`accounts.controller.ts:152` and `:673`).

#### No new i18n key

The refusal reuses `errors.transactions.payeeNotFound` ("Payee not found"),
which already exists in every full locale, rather than adding
`errors.accounts.overpaymentPayeeNotFound`. Precedent: `payees.service.ts:175`
borrows `errors.transactions.categoryNotFound` the same way. Consequence worth
noting for the verifier: **locale parity stays green** -- no catalog file was
touched, and `npm run i18n:check` passes. This was deliberate; the first draft
added an `en`-only key and turned `locales.parity.spec.ts` red (36 failures),
which the protocol tolerates on a WIP branch but which is avoidable here at no
cost.

#### Regression tests

All seven fail with the two `assertPayeeOwned` calls removed -- verified by
reverting them and re-running, not assumed:

```
AccountsService > create > assigns an owned overpayment payee
AccountsService > create > rejects an overpayment payee that does not belong to the user
AccountsService > update > assigns an owned overpayment payee on update
AccountsService > update > rejects another user's overpayment payee on update
AccountsService > update > does not store the account when the overpayment payee is rejected
account reference ids are checked for tenant ownership > requires an ownership assertion for every reference id not grandfathered above
account reference ids are checked for tenant ownership > checks the overpayment payee on both create and update
```

Two further tests deliberately pass *both* before and after -- they pin the
fix's boundaries rather than the defect: `null` still clears the field with no
lookup (otherwise the field becomes unclearable), and no lookup happens when no
payee is supplied.

New file `backend/src/accounts/account-reference-ownership.spec.ts` is the
mechanical guard `CLAUDE.md` asks for, in the shape of
`common/array-bound-dto.spec.ts`. It discovers every `*Id` property on
`CreateAccountDto`/`UpdateAccountDto` from class-validator metadata -- so a
property added later, including an inherited one, is swept without editing the
guard -- and requires each to appear as the argument of an `assert\w+Owned(`
call in the service source. Matching on the *argument* means a check written
for one field cannot be mistaken for a check on its neighbour.
