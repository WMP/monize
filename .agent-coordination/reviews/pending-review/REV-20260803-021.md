## Location

`backend/src/accounts/accounts.service.ts:734`

## Failure scenario

The update path assigns any UUID supplied as overpaymentCategoryId without checking that the category belongs to userId. An authenticated user who knows another tenant's category UUID can persist a cross-tenant relationship on their account; the equivalent institution reference immediately above is ownership-checked.

## Recommended fix

Before assignment, query the category by both ID and userId using the transaction's EntityManager, rejecting unknown or foreign IDs. Apply the same validation in the create path while still allowing null to clear.

#### What changed

`assertCategoryOwned(userId, categoryId)` added to `accounts.service.ts`,
mirroring the method of the same name in `transaction-transfer.service.ts:124`
-- same query shape, same `errors.transactions.categoryNotFound` message, so a
foreign category reads identically wherever it is refused. Called from `create`
beside the institution and payee checks, and from inside `update`'s `if` block.

On "using the transaction's EntityManager": there are no `QueryRunner`s left in
`src/` (RLS tasks R1-R7; lint rule L1 bans the pattern), and the assertion takes
no manager argument. The guarantee still holds -- a nested `withScopedDb`
**joins** the ambient transaction, so the check inside `update` runs on the same
connection inside the same transaction as the write and refuses before it. The
test `rejects another user's overpayment category on update` asserts
`manager.save` was never called.

"while still allowing null to clear" is honoured explicitly: `assertCategoryOwned`
returns early on a falsy id, and
`clears the overpayment category without a lookup when passed null` pins it. A
naive check would have made the field unclearable.

No new i18n key, so no catalog file was touched and locale parity is unaffected.

#### Regression tests

Six fail with the two `assertCategoryOwned` calls removed -- verified by
reverting them and re-running:

```
AccountsService > create > assigns an owned overpayment category
AccountsService > create > rejects an overpayment category that does not belong to the user
AccountsService > update > assigns an owned overpayment category on update
AccountsService > update > rejects another user's overpayment category on update
account reference ids are checked for tenant ownership > checks overpaymentCategoryId on both create and update
account reference ids are checked for tenant ownership > requires an ownership assertion for every reference id not grandfathered above
```

The guard's per-field both-entry-points check became an `it.each` table so the
payee and the category are each pinned to create *and* update. The sweep alone
only asks that a field reach an assertion *somewhere*, which a single-path fix
would satisfy while leaving the other door open.

Two further tests pass both before and after by design -- they pin the fix's
boundaries, not the defect: `null` clears without a lookup, and no lookup
happens when the field is absent.
