## Location

`backend/src/accounts/loan-payment-detector.service.ts:442`

## Failure scenario

The query scopes interest only by source account, category, and date range. If two active loans are paid from the same chequing account and share an interest category, both loans retrieve both sets of interest expenses. For example, $100 interest for loan A and $200 for loan B near the same monthly payment date are summed as $300 when detecting either loan, producing false inferred rates.

## Recommended fix

Associate expenses with the specific loan using payment linkage or another loan-specific discriminator. If the ledger cannot disambiguate shared source/category activity, reject inference as ambiguous instead of summing it.

## Re-review of `21bcd606ed8b`

Not fixed. Ambiguity is determined exclusively from source transactions whose linkedTransactionId resolves to another loan. Concrete failure: loans A and B are active, both configure the same chequing sourceAccountId and interestCategoryId, but B's imported principal payment has no transfer linkage. With A's $100 and B's $200 standalone interest expenses on the chequing account, no linked transaction targets B, so isAmbiguous remains false and A still pairs and sums $300. The detector explicitly supports imported/unlinked payment records, making this a reachable ledger shape.


## Re-review of `6888de3c7d51`

Not fixed. The same-category account query selects only id and never checks sourceAccountId. Concrete failure: loans A and B both configure sourceAccountId=bank-1 and interestCategoryId=cat-int, but B has no loan-account transaction in A's ±45-day query window—for example, its principal posting has not arrived yet while its $200 standalone interest expense was already imported on bank-1. The source-side lookup finds no transfer to B, otherLoanTxs is empty, and isAmbiguous returns false. The subsequent interest query then combines A's $100 expense with B's $200 expense and attributes $300 to A.
