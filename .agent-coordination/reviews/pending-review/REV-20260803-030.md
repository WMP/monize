## Location

`backend/src/loan-rate-changes/loan-rate-changes.service.ts:262`

## Failure scenario

update and remove commit the rate-history transaction before calling syncScheduledTransaction, whose errors are caught and only logged. A database or validation failure therefore returns a successful rate edit while leaving the linked scheduled bill at its old rate/payment split. The next auto-post can record incorrect principal and interest. This also violates the repository's QueryRunner invariant for operations touching multiple tables.

## Recommended fix

Make the rate-row mutation and scheduled-payment rewrite one atomic transaction using the same QueryRunner, or use an explicit preview/apply workflow that reports synchronization failure instead of swallowing it.

## Re-review of `5566c9d79ccd`

Not fixed. buildScheduledUpdate catches every error from scheduledTransactionsService.findOne and returns null. Consequently, update/remove treat synchronization as unnecessary and return success despite propagateErrors being enabled. For example, if the lookup times out or the linked scheduled row becomes temporarily inaccessible, the caller receives a successful rate edit while the scheduled payment is not rewritten; depending on the database error, the enclosing transaction may also silently roll back while the API still reports success. The added tests only reject failures from scheduledTransactionsService.update and do not cover this earlier swallowed failure path.
