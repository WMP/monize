## Location

`backend/src/accounts/loan-payment-detector.service.ts:438`

## Failure scenario

The interest transaction query filters by user, account, category, and date but not transaction status. A categorized interest expense later marked VOID is still paired and summed into a payment, producing interest and inferred-rate values from a transaction that no longer affects the ledger.

## Recommended fix

Exclude VOID transactions when querying or processing separate-interest candidates, consistently with the application's balance queries.

#### One correction to the recommended fix, and it matters

The recommendation says to exclude VOID "when querying ... consistently with the
application's balance queries". Taken literally -- `status: Not(TransactionStatus.VOID)`
in the `where` -- that introduces a second bug, so the fix deliberately does not
do it.

`transactions.status` is **nullable**: `schema.sql:274` is
`status VARCHAR(20) DEFAULT 'UNRECONCILED'` with no `NOT NULL`, and the entity
column declares no `nullable: false` either. SQL `status != 'VOID'` is `UNKNOWN`
for a NULL, so such rows are filtered out. Real interest transactions with a
NULL status would silently stop counting -- trading voided-interest-included for
interest-missing, which under `CLAUDE.md`'s missing-data rule is the worse of
the two.

That is also, on inspection, exactly what "consistently with the application's
balance queries" actually means here: every report in the codebase spells the
filter `(t.status IS NULL OR t.status != 'VOID')` --
`income-reports.service.ts:48`, `anomaly-reports.service.ts:52`,
`monthly-category-breakdown.service.ts:107` and others. The `Not(VOID)` reading
would have been *inconsistent* with them.

So the filter went in the pairing loop instead, using the entity's own `isVoid`
getter (`transaction.entity.ts:175`), immediately beside the existing
`if (tx.isTransfer) continue;`. `isVoid` is `status === VOID`, which treats NULL
as not-void by construction, needs no `Raw` SQL, and is the helper the codebase
already ships for this question. The candidate set is bounded (one category, a
~90-day window), so pushing the predicate to SQL buys nothing measurable.

#### Regression tests

`ignores a voided interest transaction while still counting its live sibling`
fails without the change (verified by removing the line and re-running; it was
the only failure). It pairs the voided row with a live row in the same category
and window, so the filter is shown to be *selective* rather than dropping the
whole batch -- a blanket `return payments` would satisfy a one-row test.

`keeps an interest transaction whose status is null` pins the nullable half. It
passes now and would fail against the `Not(VOID)` variant, so it is the test
that stops a future author "simplifying" this into the `where` clause.

Both build real `Transaction` instances via `Object.assign(new Transaction(), ...)`
rather than the object literals the rest of that describe block uses. This is
deliberate and load-bearing: the claim under test is about a **getter**, and a
plain `{ status: "VOID" }` literal has no getter, so `isVoid` is `undefined`,
the row is kept, and the test would pass against the unfixed code. That is the
"a mock must return what the real collaborator returns" trap in
`backend/CLAUDE.md`. `find()` returns hydrated entities, so the fixture is also
what the real repository hands back.

#### Adjacent, not fixed -- recommend a finding

`detectPaymentPattern` has the same gap one query up
(`loan-payment-detector.service.ts:103-109`): it loads **every** transaction on
the loan account with `where: { accountId, userId }` and no status constraint,
and feeds them to `buildPaymentRecords`, `buildRunningBalanceMap` and
`estimateInterestRate`. A voided loan payment therefore still counts as a
payment -- it can set the detected regular amount, the frequency, and the
running balance the rate estimate divides by. That is a wider blast radius than
this finding's.

No open finding covers it (REV-006/007 are at `:149`, REV-022 at `:442`,
REV-023 at `:462`). Not folded in here because it changes detected payment
amounts and inferred rates on a path this finding did not name, which is a
financial-calculation change wanting its own approval. **Recommend the review
agent raise it.**
