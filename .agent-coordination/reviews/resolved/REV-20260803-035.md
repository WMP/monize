## Location

`frontend/src/lib/loan-history.ts:391`

## Failure scenario

Separate interest is consumed once per date, but subsequent regular payments on that date fall back to analyticInterest. If an overpayment and a regular principal transfer share a date and the overpayment sorts first, it consumes the one actual interest expense; the regular row then adds a second analytic interest amount. Reversing the input order produces only the actual amount, so cumulative interest depends on transaction ordering.

## Recommended fix

Resolve all payments for a date as a group, assign the actual interest to the appropriate regular payment, and suppress analytic fallback for other rows covered by that same charge.

## Re-review of `0f6ba019ff1e`

Not fixed. For a same-day regular payment and overpayment originating from a split source transaction containing only principal transfers back to the loan, `hasOwnRecordedInterestSplit` returns false and the regular payment becomes the designated owner. However, `readRecordedInterest` treats any nonempty `linkedTransaction.splits` array as recorded-interest data and returns 0 when no non-loan split exists. The regular row therefore returns before `takeSeparateInterest`; the overpayment is blocked because it is not the designated owner; and the standalone interest expense was already paired to the date, so it is not emitted as an orphan. A real $40 interest charge consequently produces cumulative interest of $0.
